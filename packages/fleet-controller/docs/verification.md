# Verification: what the resilience tests prove, and what they do not

This page maps requirements to the tests that exercise them and says, for each,
whether the scenario is **real** (the production code path on a real on-disk
SQLite database, driven through the Hono app) or **simulated** (a stand-in for
something that cannot run here). It also lists, honestly, what has not been
verified. Where this page and a test disagree, the test wins; fix this page.

Run them with `bun test test/resilience` from `packages/fleet-controller`.

## How the tests are built

- **Real**: the controller app (`createController`, the dashboard mounted with
  `mountUi` for the security matrix), the SQLite store with its real schema, and
  the real jobs (`runOfflineSweep`, `runPrune`, `sweepOperations`, `startJobs`).
- **Restart** = closing the database connection and opening a new one on the same
  file with a new app and new in-memory state (rate limiters, caches). It is not a
  process kill (`kill -9`) and does not exercise Litestream restore or a torn WAL.
- **Time** is a hand-moved `Clock` passed as `now`. Seeded pseudo-random generators
  (a 32-bit LCG in `test/resilience/support/prng.ts`) drive the randomized runs; a
  failure names its seed. Nothing sleeps longer than a few milliseconds; the
  scheduler tests poll the real timer at 2 ms for at most half a second.
- **The node** is `SimNode` (`support/sim-node.ts`): it reports the desired revision
  it last accepted and adopts any `desired` document it receives, as `agent.py`
  does. It is a model of the agent, not the agent. The Python agent has its own
  tests under `packages/fleet/tests`, which were **not run** for this page.
- **GitHub** is a loopback fake (`test/github/testing/fake-github.ts`), never the
  real API.
- A database timestamp that SQLite writes with its own clock (`first_seen_at`,
  `approved_at`, `retired_at`) is not controlled by the injected clock; tests that
  depend on it measure from the stored value.

## Findings from writing these tests

None is silently fixed; each is either pinned by a test or reported here.

1. **First report is not always a baseline.** PROTOCOL.md says the first report
   "announces none of these". `boot`, `revision` and `role_converged` honour it;
   an approved node whose first report is already rolled back, blocked, has failed
   units or a full disk announces `rollback`, `reconcile_blocked`, `units_failed`
   or `disk_high`, once. Pinned by `failed-update-signals` "a first report that is
   already unhealthy...". Either the protocol text or the code should change.
2. **Overlapping offline sweeps announce one outage several times** (latent): the
   sweep reads due nodes, then marks and announces each, with no atomic claim. The
   scheduler's `guarded` wrapper never overlaps them and one controller owns the
   database, so it is not reachable today; a manual trigger or a second instance
   would hit it. Pinned with `test.failing` in `node-outage.test.ts`; when the claim
   becomes atomic that test starts failing and should be made a normal test.
3. **Heartbeat retention is 30 days (configurable) in code; PROTOCOL.md says 7.**
   The tests follow the code (`HEARTBEAT_RETENTION_MS`, `heartbeatRetentionDays`).
4. **No `recovering` status exists.** A node is `online`, `stale`, `offline` or its
   approval state; a return from an outage is the `recovered` event.
5. **Dashboard recovery actions** (`retry-update`, `reopen-admission`,
   `rotate-age-key`) read the node settings document and write it back with
   `putSettings` and no expected revision, so they skip the concurrency check and
   the impact analysis the API write path has, and a concurrent edit between the
   read and the write could be overwritten. Found by reading; **not** demonstrated
   by a test.
6. **Database-clock timestamps** (`first_seen_at`, `approved_at`, `retired_at`) ignore
   the injected clock; a never-reported approved node's notice timing therefore
   depends on the real wall clock in tests.

## Not covered: needs real hardware or infrastructure (none of these ran here)

| Area                                                                                                              | Why not                                                                                    | How to cover it                                                                              |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| NixOS VM tests, module evaluation (`bun run check:nix`)                                                           | Linux and Nix only; this was run on macOS without Nix                                      | Run `bun run check:nix` on Linux CI                                                          |
| Python agent, recovery outbox, `credential_rotation.py`, `runner_control.py` (`packages/fleet/tests`)             | Not executed for this page; `SimNode` only models the agent                                | Run the Python suite; add an agent-against-controller loopback test                          |
| Windows, kexec and USB installers, `fleet-node` bootstrap, image checksum and rollback of destructive installs    | Destructive; needs a disposable machine and explicit human approval naming the disk        | Disposable VM/hardware lab, never a physical disk of the operator                            |
| Real GitHub (App JWT, installation tokens, rate limits, secondary limits, runner registration, webhooks)          | Tests use a loopback fake whose behaviour is our reading of the API                        | A throwaway organization and App, behind an operator-approved CI job                         |
| Playwright/BDD browser flows (`bun run test:bdd`)                                                                 | Needs browsers and a built console; not run                                                | Run in CI                                                                                    |
| Real OIDC provider login (code + S256 PKCE)                                                                       | Session cookies are minted directly; `test/auth/*` covers the protocol against an emulator | Staging against the real provider                                                            |
| Litestream restore/replication, S3 outage, torn WAL, power loss mid-write, disk full                              | Restart here is a clean connection close                                                   | Fault-injection on the real launcher (`bun run start`) with a storage emulator and `kill -9` |
| Real clock behaviour: NTP steps, DST, node clocks that are wrong by hours                                         | Clocks are injected                                                                        | Soak test with skewed node clocks                                                            |
| Load and scale: thousands of nodes, many dashboards, heartbeat storms                                             | Largest run here is dozens of nodes and 3,000 history rows                                 | Load test the single-node deployment                                                         |
| Network faults between node and controller (TLS, proxies, partial responses, `Retry-After` honoured by the agent) | Requests are in-process                                                                    | Agent integration test through a fault-injecting proxy                                       |
| Webhook delivery to a real alert receiver                                                                         | The webhook is a recorder                                                                  | Staging receiver                                                                             |
| Multi-process / multi-instance overlap                                                                            | Unsupported by design, but see finding 2                                                   | Deployment check that only one controller can hold the volume                                |

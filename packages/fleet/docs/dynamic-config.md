# Desired state and dynamic configuration

Git is the only source of _code_: every role, closure and secrets file is defined in `roles.json`, `hosts/` and `modules/` and goes through review. The fleet controller (`packages/fleet-controller`) is the only source of _assignment_: for every node it stores a **desired state** of three parts, and the node converges on it. The wire contract is `packages/fleet-controller/PROTOCOL.md` (protocol v2); the allowed setting keys and their ranges are `packages/fleet-controller/src/config/fields.ts`. The design is [ARCHITECTURE.md](../../../ARCHITECTURE.md).

```json
{ "revision": "0123456789abcdef", "role": "ci", "closure": "ci-gpu", "values": { "sync": { "paused": false } } }
```

- **`role`**: an active role from `roles.json`, assigned by a person (node page, `PATCH /v1/nodes/:id`, approval) or by an enrollment token that names one. `null` for an unassigned node.
- **`closure`**: derived by the controller, never stored. `null` while the node is not approved (keep whatever runs), `base` for an approved node without a role, else the first of the role's closures `<role>-<cap>` whose capabilities the node's _hardware_ reports (`gpu`), else `<role>`.
- **`values`**: the typed settings below, resolved for the assigned role.
- **`revision`**: the first 16 hex digits of the sha256 of the canonical document. The node reports the one it accepted as `agent.desiredRevision`; the controller sends the document again whenever that differs.

Three rules decide everything below.

- **Data, never code.** The controller sends a role name, a flake attribute and typed values. The node checks each against what it knows and refuses the whole document if any part is wrong. It only ever builds a closure that the `roles.json` of the revision it fetched from the configured repository defines. A controller cannot make a node run a command, fetch from elsewhere or install anything Git did not define.
- **Level-triggered.** Every agent cycle (and every `fleet-sync` poll) re-reads the complete desired and observed state and acts on the difference. A lost answer, a crash, a reboot or a controller outage is harmless; the next cycle takes the same step.
- **The fleet works without the controller.** An unreachable controller leaves the last accepted desired state in force. A node that never heard from it uses its image's own role and the values built into it (`settings/shared.nix`). Reporting is best effort and can never block `fleet-sync`, a runner, or a boot.

## How a node converges

`fleet-agent` (every heartbeat, default 60 s):

1. Reports **observed** state: the role and closure of the _running_ system (`/etc/fleet/node.conf`), hardware capabilities (`gpu` when an NVIDIA display controller is on the PCI bus), the node's public age recipient (`age.pub`), `agent.desiredRevision` and fleet-sync's last verdict (`reconcile`). A report never changes the assignment.
2. Receives `desired` when its revision differs, validates it (the role is active or `null`; the closure is `base` only without a role, otherwise `<role>` or `<role>-<cap>`; the revision is 16 hex; values is an object) and persists it to `/nix/fleet-state/agent/config.json`. An invalid document is logged and refused whole; the cached one stays.
3. Applies the settings (table below) and writes `/nix/fleet-state/target` (`role=…`, `closure=…`, root `0644`, atomic) when the closure is not `null` and the file differs, then starts `fleet-sync` with `systemctl start --no-block`. Every cycle does this again from the cache, so a missing or damaged target is repaired.

`fleet-sync` (every `repo.pollSeconds`, default 300 s) reads the target (else the image's own `ROLE`/`FLAKE_ATTR` from `/etc/fleet/sync.env`; a malformed target is ignored with a logged reason), fetches `main`, refuses a target the fetched `roles.json` does not define, and refuses a role whose secrets file does not list this node's age recipient (`FLEET_SECRETS_RECIPIENT_MISSING`). It then builds and switches as before. A target role different from the running role is a reboot-class change: drain, `switch-to-configuration boot`, staggered reboot, fallback and rollback ([resilience.md](resilience.md)). Every run ends with `/run/fleet/reconcile.json`: `{ phase, issues, role, closure, revision, at }`, where phase is `converged`, `progressing` or `blocked`. The agent reports it, and the node page and the node console show it.

### Local mode

Without `fleetApi.url` there is no agent. `fleet-target set ci|devbox|base [CLOSURE]` writes the same target and starts `fleet-sync`; `fleet-target clear` returns to the image's own role; `fleet-target show` prints the running and target role and the verdict. With a controller configured, `set` and `clear` refuse: the controller is authoritative.

### Runner repositories and labels, in detail

The agent writes `/run/fleet/assign/<slot-id>` (one `owner/repo` line) for every slot in the closure, so a later increase in capacity already has its assignment. Runners are ephemeral and register again after every job, so:

1. The registration pre-start of each slot (`fleet-register-<slot>` in `modules/runners.nix`) reads `/run/fleet/assign/<slot>`. A valid name makes it ask the GitHub App for a registration token for that repository; otherwise it uses the static `settings.github` scope exactly as before. It records the repository it used in `/run/fleet/assign-used/<slot>`.
2. The `Runner.Listener` wrapper reads that record at `configure` time and rewrites `--url` to `https://github.com/<repo>`, and drops `--runnergroup` (an organization-only option). It appends the extra labels to `--labels`. Reading the record rather than the assignment means the token and the URL always name the same repository, even if the setting changes in between.
3. `fleet-drain` also drains every repository in `assign-used`, so a reboot never kills a job that runs for an assigned repository. A repository GitHub cannot be asked about does not block updates; the drain then waits for the local job markers (`/run/fleet/<slot>/busy`).
4. When assignments or labels change, the agent restarts the **idle** slots whose assignment changed (all idle slots for a label change) with `systemctl try-restart --no-block`. A busy slot keeps its job and picks up the change after it.

### Capacity changes

The agent rewrites `/run/fleet/slot-count` and restarts `fleet-capacity.service` (`--no-block`). That unit starts the slots up to the count and stops the surplus slots that are **idle**. It takes the same lock as the job-start hook, so a job cannot start between the check and the stop. A busy surplus slot is never stopped; it is written to `/run/fleet/capacity-pending` and the agent asks again at every report until it is gone.

## Safety

- Every file is read through `scripts/fleetconf.py`. A missing or corrupt file, a key that is not in its table, a value of the wrong type or outside the range, a repository name that is not `owner/name` (or has a `.`/`..` part), a list with a reserved or repeated label: each of these is ignored and the built-in value applies. A unit never fails because of a setting.
- The same table is applied twice: by the controller when a person saves a setting (strict, a typo is an error) and by the node when it receives one. `tests/test_agent.py` checks that both lists have the same keys.
- Each application step is independent. A failing step is logged, reported as a `config` warning event in the next heartbeat, and does not stop the others.
- A node that is `pending` (not yet approved) is sent only `heartbeat.intervalSeconds` and `closure: null`: it keeps what it runs and no target is written. Receiving a new document replaces the whole previous one, so a node that lost its approval returns to the built-in values (and keeps its last target).
- Applying the same settings twice changes nothing: files are rewritten atomically (never truncated in place) and only when their content differs.
- After a reboot the settings are applied again from the cache before the controller is reached: `cattle.py identity` writes labels, slot count and assignments from `/nix/fleet-state/config.json`, and the agent re-applies its cache on start.

## Where things live

Nodes are stateless: `/nix` holds the Nix store, the node's identity and caches. Identity is the allow-list `IDENTITY` in `scripts/node_state.py` (credential, enrollment token, desired-state cache, age identity, Git credential, SSH host keys, Wi-Fi, target, update and recovery records). Everything else, including anything a module writes without declaring it, is cache and is wiped at the first boot of a different role. `node_state.py show` prints what a role change would wipe.

Tools on every node: `fleet-agent status` (no network; prints the last outcome, the running, assigned and target role and the convergence phase, never a secret), `fleet-target show|set|clear`, `fleet-agent once` (one report now), `fleet-agent retire`, and `fleetconf get KEY DEFAULT` / `fleetconf dump`. `fleet-remove` runs `fleet-agent retire` after the runner is withdrawn and before the power off, with a 10 second limit; a failure there never blocks the removal.

The agent is left out of an image whose `fleetApi.url` in `settings/shared.nix` is empty or contains `TODO`. Nothing reports then, every setting keeps its built-in value and `fleet-target` is the source of the target (local mode).

### Enrolling without a person

The controller may hold up to 16 enrollment tokens (`FLEET_ENROLLMENT_TOKENS`, a JSON array of `{ "sha256", "role" }`; only the sha256 is stored). The installer may place one on the node as `/nix/fleet-state/agent/enrollment-token` (`0600`, directory `0700`); the agent validates it (8..512 characters from `A-Za-z0-9._-`), sends it only in the registration request and never logs or prints it. A matching token approves the node and, when its entry names a role and the node has none, assigns that role. Without a token the node registers as `pending` and a person approves it in the dashboard, optionally with a role. `FLEET_ROLE_TOKEN_HASHES` is refused by the controller; map each old hash to its role in `FLEET_ENROLLMENT_TOKENS`.

## What deliberately stays in git

Everything that decides what the machine is or can reach, because it must go through review, the merge queue, the binary cache and the health-checked rollback:

- Which roles and closures exist and what they contain (`roles.json`, `hosts/`, `modules/`), the NixOS version and the flake lock. The controller only chooses among them.
- The GitHub App identity and scope: `settings/github.json`, imported as `settings.github` (`appId`, `installationId`, `organization`, `scope`, `runnerGroup`).
- Secrets and their SOPS recipients, `repo.url`, `repo.auth`, `binaryCache`, the sync poll interval, `drift.maxMinutes`, the boot generation limit and tries, root SSH keys, `reboot.drainCommand` and the drain timeout, `fleetApi.url` itself.

The dashboard can assign only a role `roles.json` defines and change a value only inside the range the node accepts, and only for the keys above.

## Security model

- **Data, not code.** There is no key whose value is a command, a path, a unit name, a URL or a script. The role and closure are names matched against a pattern, written to a root-owned file, and then only used as a flake attribute of the fetched, reviewed revision, after `roles.json` at that revision confirmed it. Repository names and labels are matched against a pattern, written to root-owned files, and only ever used as one argument of the GitHub registration URL or of `--labels`. SSH keys are matched against a strict key pattern with no options. Nothing is interpolated into a shell or a unit.
- **The App installation bounds repositories.** A repository can only register runners if the GitHub App behind `settings.github.appId` is installed on it: the registration token request for any other name fails (`fleet-register-<slot>` exits non-zero, so that slot's unit keeps failing and retrying and never registers). A compromised or mistaken `runners.repositories` can therefore redirect where runners work only inside the set the owner already installed the App on, which `just setup --repos` chose by hand because a public repository would run strangers' pull requests on the fleet. Never install the App on such a repository.
- **Secrets stay behind Git review.** Every node generates its own age identity; only the public recipient is reported. A role's secrets file is encrypted, in the operator's own repository, to the recipients of the nodes assigned that role (`GET /v1/recipients`) plus the operator's keys. Fleet never holds a private age key, never writes to Git and never changes GitHub settings. A node assigned a role whose file does not list it stays where it is and reports `FLEET_SECRETS_RECIPIENT_MISSING`. A devbox's identity is never a recipient of the CI file.
- **A compromised controller can** change a node's role among the roles Git defines, and therefore which reviewed closure it runs and which runner credentials it could decrypt _if_ the operator already made it a recipient of that role's file; grant unprivileged `dev` logins on devboxes through `devbox.authorizedKeys`; pause updates, cordon or disable runners, move slots between the allowed repositories, add labels, lower capacity or raise it up to the units in the closure, hide a disk alert, stop a reboot, retry a quarantined kernel (which can cost one more fallback cycle of three boots) or lift a manual drain. All of these are assignment, availability or routing effects of the kind a person could cause in the dashboard anyway, and each is visible: the heartbeat reports the running role, `sync.paused` and the convergence phase, and `fleet-drift` still fails when the node is behind `main`. **It cannot** execute anything on a node, choose code outside the reviewed repository, read a secret or obtain a private age key, add a SOPS recipient, give root SSH access (root keys stay in Git), point a node at another Git repository or cache, skip drain, health checks or rollback, or make a node boot anything but a system the reviewed revision defines.
- **Transport and credentials.** TLS verification is on, redirects are not followed (they would carry the token), requests have timeouts, responses are capped at 1 MiB, and a non-HTTPS address is refused (the loopback address is allowed for tests). Authentication is `Bearer <node id>.<node secret>`. Neither the node secret nor the enrollment token is logged, put in an event, or written outside its own file, and every log line and reported issue is passed through a redactor.
- **A stolen enrollment token** lets another machine register as `approved` and, if the token names a role and the machine has none, be assigned that role. It then receives that role's (non-secret) settings and a place in the dashboard, and converges to the role's closure, but its own age identity is not a recipient of the role's secrets, so it decrypts nothing and stays `blocked`. Rotate a token by replacing its hash in `FLEET_ENROLLMENT_TOKENS`.
- **Privacy.** The controller learns each node's hostname, running and assigned role, closure, hardware capabilities, public age recipient, addresses, kernel, revision, load, memory, disk percentages, failed unit names, runner slot counts, the convergence verdict and a few events. It learns no job, repository content or secret.

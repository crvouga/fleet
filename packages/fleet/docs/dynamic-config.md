# Dynamic configuration

Git stays the control surface for what a node _is_ (its role, its closure, its secrets). A small set of tunables is changed from the fleet dashboard instead, with no commit and no rebuild. Every node runs `fleet-agent`, which sends the fleet API (`packages/fleet-api`) a heartbeat and receives the node's settings in the answer. The wire contract is `packages/fleet-api/PROTOCOL.md`; the allowed keys and their ranges are `packages/fleet-api/src/config/schema.ts`.

Two rules decide everything below.

- **Data, never code.** The API sends typed values. The node interprets the keys listed here and ignores everything else. A server cannot make a node run, fetch or install anything.
- **The fleet works without the API.** An unreachable server leaves the last applied settings in force. A node that never heard from it uses the values built into its image (`settings/shared.nix`). Reporting is best effort and can never block `fleet-sync`, a runner, or a boot.

### Runner repositories and labels, in detail

The agent writes `/run/fleet/assign/<slot-id>` (one `owner/repo` line) for every slot in the closure, so a later increase in capacity already has its assignment. Runners are ephemeral and register again after every job, so:

1. The registration pre-start of each slot (`fleet-register-<slot>` in `modules/runners.nix`) reads `/run/fleet/assign/<slot>`. A valid name makes it ask the GitHub App for a registration token for that repository; otherwise it uses the static `settings.github` scope exactly as before. It records the repository it used in `/run/fleet/assign-used/<slot>`.
2. The `Runner.Listener` wrapper reads that record at `configure` time and rewrites `--url` to `https://github.com/<repo>`, and drops `--runnergroup` (an organization-only option). It appends the extra labels to `--labels`. Reading the record rather than the assignment means the token and the URL always name the same repository, even if the setting changes in between.
3. `fleet-drain` also drains every repository in `assign-used`, so a reboot never kills a job that runs for an assigned repository. A repository GitHub cannot be asked about does not block updates; the drain then waits for the local job markers (`/run/fleet/<slot>/busy`).
4. When assignments or labels change, the agent restarts the **idle** slots whose assignment changed (all idle slots for a label change) with `systemctl try-restart --no-block`. A busy slot keeps its job and picks up the change after it.

### Capacity changes

The agent rewrites `/run/fleet/slot-count` and restarts `fleet-capacity.service` (`--no-block`). That unit starts the slots up to the count and stops the surplus slots that are **idle**. It takes the same lock as the job-start hook, so a job cannot start between the check and the stop. A busy surplus slot is never stopped; it is written to `/run/fleet/capacity-pending` and the agent asks again at every report until it is gone.

## Safety

- Every file is read through `scripts/fleetconf.py`. A missing or corrupt file, a key that is not in its table, a value of the wrong type or outside the range, a repository name that is not `owner/name` (or has a `.`/`..` part), a list with a reserved or repeated label: each of these is ignored and the built-in value applies. A unit never fails because of a setting.
- The same table is applied twice: by the server when a person saves a setting (strict, a typo is an error) and by the node when it receives one. `tests/test_agent.py` checks that both lists have the same keys.
- Each application step is independent. A failing step is logged, reported as a `config` warning event in the next heartbeat, and does not stop the others.
- A node that is `pending` (not yet approved) is sent only `heartbeat.intervalSeconds`. Receiving a new document replaces the whole previous one, so a node that lost its approval returns to the built-in values.
- Applying the same settings twice changes nothing: files are rewritten atomically (never truncated in place) and only when their content differs.
- After a reboot the settings are applied again from the cache before the API is reached: `cattle.py identity` writes labels, slot count and assignments from `/nix/fleet-state/config.json`, and the agent re-applies its cache on start.

## Where things live

| Path                                                                            | Content                                                                                                                                        |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `/nix/fleet-state/agent/node.secret`                                            | 32 random bytes, hex, `0600`. Created on first run. The server stores only its sha256. A new secret (reinstall, deleted file) registers again. |
| `/nix/fleet-state/agent/role-token`                                             | Optional, `0600`, from the installer. Lets the node register as `approved` without a person.                                                   |
| `/nix/fleet-state/agent/config.json`                                            | The last document received: `{ "revision", "values" }`. The revision is what the agent reports as `agent.configRevision`.                      |
| `/nix/fleet-state/agent/reported.json`, `status.json`                           | Last boot id and event markers (so an event is sent once); the last report outcome for `fleet-agent status`. No secret.                        |
| `/nix/fleet-state/config.json`                                                  | The valid settings, nested as the API sends them. The file `fleetconf` reads.                                                                  |
| `/run/fleet/config.json`                                                        | The same, for a person looking at a running node.                                                                                              |
| `/run/fleet/runner-labels`, `slot-count`, `assign/<slot>`, `assign-used/<slot>` | Runtime files described above.                                                                                                                 |
| `/run/fleet/agent-drained`, `capacity-pending`, `reboot-pending`                | Markers: a drain the agent started, slots waiting for their job, a kernel waiting for `reboot.enabled`.                                        |

Tools on every node: `fleet-agent status` (no network; prints the last outcome, never a secret), `fleet-agent once` (one report now), `fleet-agent retire`, and `fleetconf get KEY DEFAULT` / `fleetconf dump`. `fleet-remove` runs `fleet-agent retire` after the runner is withdrawn and before the power off, with a 10 second limit; a failure there never blocks the removal.

The agent is left out of an image whose `fleetApi.url` in `settings/shared.nix` is empty or contains `TODO`. Nothing reports then and every setting keeps its built-in value, exactly as before the agent existed.

### Enrolling without a person

The wrapped enrollment document that holds a role's age key (`secret/data/fleet/<role>`, field `age_key`) may also hold `api_token`: the role token for that role. `fleet-install` validates it like the key (printable, no spaces, 8..512 characters from `A-Za-z0-9._-`), installs it as `/nix/fleet-state/agent/role-token` (`0600`, directory `0700`) and never prints it. A document without it is fine; the node then registers as `pending` and a person approves it in the dashboard. The server holds only the sha256 of each role token (`FLEET_ROLE_TOKEN_HASHES`).

## What deliberately stays in git

Everything that decides what the machine is or can reach, because it must go through review, the merge queue, the binary cache and the health-checked rollback:

- Roles, capabilities and their closures (`roles.json`, `hosts/`, `modules/`), the NixOS version and the flake lock.
- The GitHub App identity and scope: `settings/github.json`, imported as `settings.github` (`appId`, `installationId`, `organization`, `scope`, `runnerGroup`).
- Secrets and age keys, `repo.url`, `repo.auth`, `binaryCache`, the sync poll interval, `drift.maxMinutes`, the boot generation limit and tries, SSH keys, `reboot.drainCommand` and the drain timeout, `fleetApi.url` itself.

The dashboard can change a value only inside the range the node accepts, and only for the keys above.

## Security model

- **Data, not code.** There is no key whose value is a command, a path, a unit name, a URL or a script. Repository names and labels are matched against a pattern, written to root-owned files, and then only ever used as one argument of the GitHub registration URL or of `--labels`. They are never interpolated into a shell or a unit.
- **The App installation bounds repositories.** A repository can only register runners if the GitHub App behind `settings.github.appId` is installed on it: the registration token request for any other name fails (`fleet-register-<slot>` exits non-zero, so that slot's unit keeps failing and retrying and never registers). A compromised or mistaken `runners.repositories` can therefore redirect where runners work only inside the set the owner already installed the App on, which `just setup --repos` chose by hand because a public repository would run strangers' pull requests on the fleet. Never install the App on such a repository.
- **A compromised API can** pause updates, cordon or disable runners, move slots between the allowed repositories, add labels, lower capacity or raise it up to the units in the closure, hide a disk alert, stop a kernel reboot, retry a quarantined kernel (which can cost one more fallback cycle of three boots) or lift a manual drain. All of these are availability or routing effects of the kind a person could cause in the dashboard anyway. Pausing updates is visible: the heartbeat reports `sync.paused` and `fleet-drift` still fails when the node is behind `main`. **It cannot** execute anything on a node, read a secret or age key, change a role or closure, point a node at another git repository or cache, or make a node reboot into anything but a system the Fleet workflow built and cached.
- **Transport and credentials.** TLS verification is on, redirects are not followed (they would carry the token), requests have timeouts, responses are capped at 1 MiB, and a non-HTTPS address is refused (the loopback address is allowed for tests). Authentication is `Bearer <node id>.<node secret>`. Neither the node secret nor the role token is logged, put in an event, or written outside its own file, and every log line is passed through a redactor.
- **A stolen role token** lets another machine register as `approved` for that role and receive its (non-secret) settings and a place in the dashboard. It grants no access to age keys, secrets or other nodes. Rotate it by changing the hash in the server's `FLEET_ROLE_TOKEN_HASHES` and the value in the vault document.
- **Privacy.** The server learns each node's hostname, role, addresses, kernel, revision, load, memory, disk percentages, failed unit names, runner slot counts and a few events. It learns no job, repository content or secret.
